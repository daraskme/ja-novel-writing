# 表記・媒体別体裁・字数・AI 利用申告

- いつ読むか: 校閲するとき（lint の N 群・M 群が鳴った、校閲役を回す）、投稿先・応募先へ書き出すとき、字数や枚数を答えるとき、生成 AI 利用の申告や公募の AI 規定が話題になったとき。
- いつ読まないか: 執筆中。字下げと約物の既定は SKILL.md と lint で足りる。表記を気にしながら書くと場面が痩せる。

媒体の仕様は 2026-09-19 に、各サイトの公式ヘルプ・ガイドラインと各賞の公式要項の本文を直接読んで確かめた内容である。確かさを記号で示す。

| 記号 | 意味 |
|---|---|
| [確] | 公式ヘルプ・ガイドライン・要項の本文で確認 |
| [準] | 運営の公式 API 文書などで確認 |
| [二] | 個人記事にしか無い。公式の記載は見つからなかった |
| [未] | 裏が取れていない |
| [慣] | 界隈の慣習。規定ではない |

この資料に無い仕様と [二]・[未] の仕様は、断定形で答えない。「未確認」と言い、公式ページを取得するか、ユーザーに該当箇所を貼ってもらう。LLM は投稿サイトの仕様を古い記憶や他サイトとの混同でもっともらしく答える。「pixiv は Markdown が効く」「pixiv は 1 投稿 5 万字まで」「公募は 40 字×30 行が標準」は、どれも根拠が見つからなかった。

## 1. 前提

- 投稿先・応募先の規定が最上位。公募は枚数・書式・ファイル形式・梗概の違反で読まれずに落ちるので、ここだけは「破ってよい場合」が無い。
- 変換と計数はスクリプトに任せる。記法の置換を手でやると、記法だけのつもりで語句まで整えてしまう。字数を目で数えると外す。`export.py` と `count_chars.py` を使い、告げる値は実測だけにする。
- 仕様の寿命は種類で違う。記法（ルビ等）は数年単位で安定している。上限値は参考値で、近づいたら公式で再確認する。AI 規定と公募要項は数か月で変わるので固定値として扱わず、§7・§8 の手順で毎回確かめる。
- ユーザーの既存原稿の表記が一貫しているなら、それは文体の一部である（§2.4）。

## 2. 本文の表記規則

### 2.1 早見表

機械で拾えるものは lint の N 群（表記）が位置を出す。字下げは N05、表記ゆれは G 群、前置きや応答文の混入は M 群。

lint が FAIL にするのは、地の文と、台詞と分類できた引用の中の表記だけ。書名（『おやすみ。』）、固有名（「モーニング娘。」）、入力文字列（「...」と入力した）、台詞の中の引用は、台詞用の規則を当てると題名や文字列そのものを書き換えてしまうので、lint がそう検知できた場合は N09（引用の中の表記・要確認）として WARN に回る（検知には取りこぼしがあり、FAIL に混じることもある）。N09 は、それが台詞なら N01〜N04 の規則で直し、題名・固有名・文字列そのものなら残す。括弧の対応が崩れた行は N08 が知らせる。字下げされた原稿の中で、字下げの無い行が 2 行以上まとまっている所や、前の段落が「チャットを開いた」「貼り紙があった」のように文書を導入している所は、作中文書（チャット・手紙・貼り紙・献立・歌詞）とみなし、字下げの混在（N05 FAIL）の根拠にせず WARN で知らせる。その中の約物も N09 に回る。1 行だけ字下げが無いのは下げ忘れとして FAIL。どの FAIL も、直す前にその箇所を読んで誤りと確かめる。

| 項目 | 既定 | なぜ | 破ってよい場合 |
|---|---|---|---|
| 段落頭 | 地の文は全角空白 1 個で下げる。開き括弧で始まる段落は下げない | 商業出版の標準（§4） | §4 |
| 会話 | 「」で括り、閉じ括弧の直前に句点を打たない。1 つの「」に 1 発話。「」の中で改行しない | 商業小説の標準で、下読みは 1 ページ目のここで推敲の有無を測る。「」内の改行は lint の地の文・台詞の分離も壊す | 児童書、絵本調の作中作 |
| 三点リーダー | `……`（U+2026 を 2 個）。伸ばすなら 4 個、6 個と偶数で | 組版では 2 個で 1 本。LLM は `…` 1 個、`...`、`・・・` を混ぜる | 作中のチャット文面・手書きメモの再現 |
| ダッシュ | `――`（2 個）。コードポイントは作品内で 1 種類にし、既定は U+2015 | 1 個だと長音や漢数字の「一」と紛れる。LLM は欧文の `—`（U+2014）1 個、`ーー`、`--` を出す | 既存原稿が罫線 `──` で統一しているならそのまま |
| 感嘆符・疑問符 | 全角。`！？` は全角 2 字。直後に全角空白 1 個。閉じ括弧の直前、段落末、記号の連続の間（`！？` `！！`）には入れない | 縦組で次の字と詰まる。半角 `!?` は縦書きで横倒しになる | — |
| 数字 | 漢数字。慣用句・固有語（一人、二度と、四天王）は媒体を問わず漢数字。数量は単位語つき（二十三人、三百円）、西暦・番地は位取り（二〇二六年）。型番・部屋番号・時刻表示・作中の画面表示は算用数字 | 縦書きへそのまま出せる。LLM は同じ話の中で「1人」と「一人」を混ぜる | 横書き専用の作品で算用数字に統一する（文体シートに書く）。ステータス画面のある Web 作品 |
| 括弧 | 「」会話／『』会話内の引用・書名／（）心内語か補足／〈〉強調・固有概念。`《 》` はルビと傍点の専用で、素では使わない | `《 》` は投稿サイトでルビに化ける（§3） | 心内語を（）にするか地の文に溶かすかは、作品で一方に決める |
| 改行と禁則 | 1 段落 1 行。禁則を避けるための手動改行を入れない | 表示幅は環境で変わる。行頭・行末の禁則は表示側と組版の仕事 | 詩・歌詞・手紙の引用 |
| 文字種 | 半角カナ、機種依存文字、絵文字、顔文字を入れない。波ダッシュ（`〜` と `～`）は作品内で 1 種類に | なろうは絵文字・機種依存文字を保存エラーの原因と明記 [確]。公募の .txt 応募でも化ける | 作中のメッセージ画面の再現（投稿先で通るか確かめる） |
| Markdown | 本文に `**`、箇条書き、`---`、引用記号を入れない。見出しはファイル先頭の章題 1 行まで | 投稿欄ではそのまま文字として出る。プロンプトや応答文の残骸と並んで、運営対応の対象にしているサイトがある（§8） | — |
| 表記ゆれ | 私／わたし、分かる／わかる等は作品ごとに一方へ固定し、`style/glossary.toml` に登録 | 一人称の表記が揺れると別人に見える。漢字をひらく方針そのものは文体シートの字面で決める | 人物ごとに表記を変える設計（声シートに書く） |

### 2.3 手本

内部記法（§3）で書いた正本の例。字下げ、`！` `？` の後の全角空白と閉じ括弧前の詰め、リーダーとダッシュ、「」の中の『』、漢数字、ルビ、傍点、場面転換を含む。

```
　七時の便は、客が三人と単車が一台だった。須波は舫い綱を外してから、首に下げた集金鞄の口を開けた。
「おっちゃん！　これ｜向島《むかいしま》行く？」
　単車の男が船のエンジンに負けない声で訊いた。ヘルメットの顎紐は留めずに垂らしたままだ。
「行くよ。ここから出る船はみな行く」
「よかった……『七時の便に《《必ず》》乗せえ』言われとって」
　乗せろと言われたのは、どうやら荷物のほうだった。荷台に括りつけた発泡スチロールの箱は蓋の合わせ目にガムテープが二重に巻いてあり、男はそれを片手で押さえたまま、もう片方の手で上着の内ポケットを探っている。
「百円。単車は別に十円」
「――あ、細かいのが」
「向こうでええよ。降りるときにな」
　対岸まで四分かかる。須波は箱の中身を訊かなかった。側面に油性ペンで、寿し二十人前、と書いてある。
＊
　最終便に、男は空の荷台で乗ってきた。須波が手を出すより先に、百円玉を二枚と十円玉を二枚、鞄の口へ落とした。
```

箱の文字は括弧に入れず、読点で挟んで地の文に溶かしてある。物に書かれた短い文字を「」に入れると、lint が台詞として数える。

### 2.4 既存原稿の表記を直す範囲

ユーザーの原稿が `。」` を一貫して打つ、字下げなしで統一している、罫線 `──` を使う、といった場合は、誤りではなく流儀として扱う。直すのは混在だけにして、公募へ出すと不利になりうる点を 1 行で伝える。lint の FAIL を理由に全部を既定へ寄せると、作者が選んだ字面を無断で標準化することになる。意図した破格（チャット文面、作中作、詩）は文体シートの例外宣言に書き、以後の校閲で蒸し返さない。N04 を止めるなら、`style/lint.json` の overrides に `{"N04": {"off": true, "reason": "閉じ括弧前の句点を作者の流儀として残す"}}` と書く。

## 3. 内部記法（正本の書き方）

正本はこの記法で持ち、投稿先の記法へは `export.py` が変換する。この 2 記法にした根拠: カクヨム・なろう・ハーメルン・ノベルアップ＋でルビがそのまま通り、カクヨム・ハーメルンでは傍点もそのまま通り、pixiv も Web 版エディタの記法変換がこの 2 つだけを受け付ける [確]。

| 要素 | 書き方 | 注意 |
|---|---|---|
| ルビ | `｜親文字《るび》` | ｜は全角縦線。省略しない |
| 傍点 | `《《語》》` | 同じ語にルビと重ねない（カクヨムで無効 [確]） |
| 場面転換 | `＊` だけの行 | 字下げしない。`---` や `* * *` は Markdown の水平線・箇条書きに化ける |
| 段落 | 1 段落 1 行 | 段落内で改行しない |
| 空行 | 既定では入れない。入れるなら時間の小さな飛びを示す一行アキとして 1 行だけ | Web 向けの空行は書き出し時に付ける（§5.3）。正本から空行ありで統一する作品は文体シートに書く |
| 章題 | ファイル先頭の見出し 1 行まで | 投稿欄の本文には残さず、題の欄へ入れる |
| メタ情報 | 本文ファイルに入れない | 題・あらすじ・タグ・AI 申告区分は別ファイルに。HTML コメントで埋めると、消し忘れがそのまま公開される |

ルビと括弧の規則:

- ｜を省略しない。省略形の解釈は媒体ごとに違い（漢字のみ／漢字と半角英数／ルビがかなの場合のみ）、アルファポリスと pixiv への変換では親文字の境界が決められない。`export.py` は省略形を変換せず WARN を出す。
- 素の `《 》` を本文で使わない。カクヨム・なろう・ノベルアップ＋ではルビに化け、ハーメルンでは山括弧ベースの特殊タグとも衝突する [確]。固有概念の括りは〈 〉、強調は傍点。
- ルビ・傍点を改行またぎにしない（カクヨムで無効 [確]）。
- 漢字や半角英数の直後に、かなだけの丸括弧を置かない。`山田(やまだ)` `山田（やまだ）` はなろうで、全角丸括弧と半角英数の親文字はノベルアップ＋でも、勝手にルビになる [確]。読みを示したいならルビにする。補足の括弧として残すなら括弧の直前に｜を置く。
- ルビを振るのは難読語・造語・当て字の初出。LLM は人名に出るたび振るか、造語に一度も振らないかのどちらかに振れる。当て字ルビ（漢語にカタカナを振る型）の量はジャンル契約で決める。戦闘もののラノベでは様式として多くてよく、それ以外で重なると失笑を買う。
- ルビの長さは、最も厳しいなろう（親 10 字・ルビ 10 字）に収めればどこでも通る。
- 題・あらすじ・キャッチコピーにルビや傍点の記法を残さない。カクヨム・なろうでは本文以外で効かず、記号がそのまま表示される [確]。

## 4. 字下げ

資料によって「原稿に入れる」「入れない」「Web は不要」と割れて見えるが、述べている層が違うだけで矛盾していない。裁定は次のとおり。

| 層 | 裁定 |
|---|---|
| 正本 | 既定は字下げあり（`novel.toml` の `[format] indent = "fullwidth"`）。flash・short で会話に直接出す本文も同じ。LLM の自然な出力と一致し、そのまま体裁を満たす |
| lint（N05） | 混在・形の誤り（半角空白・タブ・全角 2 個以上）と、`novel.toml` の `[format] indent` との不一致は FAIL。設定が無く字下げなしで統一されていれば、web 以外では INFO（`export.py` で付与可） |
| 書き出し | `export.py --indent add / keep / remove`。プロジェクト外では add が既定。`novel.toml` の indent が fullwidth か none なら keep、export なら add が既定になる |
| `indent = "export"` | 正本は字下げなしで持ち、書き出し時に付ける。エディタや編集経路で行頭の全角空白が落ちる事故が出た環境で選ぶ |
| `indent = "none"` | 字下げなしと多めの空行で統一する Web 作品。公募や紙へ回すときは `--indent add` を明示する |

付与の規則: 全角空白 1 個を地の文の段落頭にだけ。`「『（【〈《` で始まる段落、場面転換行、空行、見出しは下げない。すでに全角空白で始まる段落は二重にしない。`《《` で始まる段落は傍点つきの地の文なので下げる。

原稿側に入れておく理由: なろうの「自動字下げ」とカクヨムの「段落先頭を字下げ」は、読者側の表示機能ではなく、原稿テキストに全角空白を書き込むエディタのボタンである [確]。ノベルアップ＋にも同種のボタンがある（条件の記載なし）[確]。アルファポリス・pixiv・ハーメルンでは同種の機能の記載を見つけられなかった [未]。原稿に入っていなければ表示もされず、入っていればどこでもそのまま通る。なろうのボタンは空白のある行を二重に下げないので、後から押されても壊れない。なろうのヘルプが除外を明記しているのは `「` 始まりだけで、`『` や `（` 始まりの行の扱いは記載がない [未]。自前で入れておけば、（ 始まりの心内語の行が下がる事故を避けられる。

崩れ方: 長い出力の後半で字下げが消える。会話の行まで下げる。部分編集で行頭の全角空白を落とす（Edit の置換文字列に含め忘れる）。ここまでは N05 が拾う。字下げなしで統一された既存原稿を、頼まれていないのに字下げありへ直す事故は lint に出ないので、revise モードでは着手前に原稿の流儀を見る。

破ってよい場合: チャットログ風の演出、詩的な行分け、作中の手紙や掲示の再現。文体シートに例外として書く。

`export.py --to` の出力先は narou / kakuyomu / alphapolis / pixiv / plain。実装は [確] の記法だけで、未確認の記法は変換しない。

- ハーメルンは対応範囲内の記法をそのまま貼る。ノベルアップ＋は `--to kakuyomu` の出力を貼り、傍点はエディタの置換操作を行ってプレビューで確認する。ルビ長の警告はカクヨムの上限で出るので、各サイトの上限は表と照合する。
- なろうとアルファポリスの傍点は変換されず、`《《語》》` のまま残って WARN が出る。投稿画面の入力補助で付けてもらうか、`--bouten strip` で記号を外すか、傍点なしで通じる文にするかをユーザーに選んでもらう。
- pixiv は 2 通り。スクリプトで特殊タグへ変換して貼る（確実。既定）か、`--to kakuyomu` の出力を Web 版エディタに貼って置換ボタンを押す（手軽だがアプリ不可）。ユーザーに選ばせる。

### 5.3 空行と縦書き原稿

- Web 横書き: 会話と地の文の間や、地の文の数行ごとに空行を入れる流儀が主流 [慣]。スマホの縦スクロールでは紙の密度が壁に見えるため。1 文ごとの空行は緩急を消す。一般文芸寄りの読者層や pixiv の文芸寄りのコミュニティは空行少なめを好む [慣]。作品で一方に決め、書き出しの `--blank dialogue`（地の文と会話の境目）か `--blank para`（全段落の間）で付ける。
- 縦書き公募原稿: 空行は場面転換だけ（`--to plain --blank none`）。Web 式の空行だらけの原稿は枚数の水増しにも見える。数字は漢数字、`！？` は全角、英字と 2 桁数字の扱い（全角か縦中横か）は要項に従う。ノンブル、題と筆名の位置、1 枚目の記載事項も要項どおりに。
- Web 原稿を公募へ回すときは、空行の除去・算用数字の漢数字化・半角記号の全角化が要る。`export.py` は本文を直さないので、数字と記号は正本で直す。算用数字の置換は慣用句と型番を巻き込むため、一括置換せず 1 件ずつ見る。

### 5.4 書き出しの手順

```
python "SKILL_DIR/scripts/novel_lint.py" manuscript/ch001.md --project .
python "SKILL_DIR/scripts/export.py" manuscript/ch001.md --to narou --verify
python "SKILL_DIR/scripts/count_chars.py" manuscript/ch001.md --mode narou
```

1. lint の N・M・C 群の FAIL を確認・処置してから書き出す。確かめた誤りは正本で直す。誤検出や作者の流儀として残すものは、理由を残して keep（未確認・未処置の FAIL を残したまま書き出さない）。
2. 変換は `export.py` に任せる。変換のたびに出力を内部記法へ戻して正本と突き合わせ、本文が 1 字でも違えば書き出さずに終了コード 1 で止まる。`《《 》》` と `《 》` は入れ子で衝突するので、手作業の置換は順序を誤って壊しやすい。
3. 出力で誤字や表記の誤りに気づいても、出力側では直さない。正本を直して書き出し直す。出力だけ直すと次の書き出しで元に戻る。出力を手で触った後は `--verify-file` で正本との一致を確かめる。
4. 題・あらすじ・タグ・AI 申告区分は本文と別のファイルで渡す。作品に無い要素のタグは付けない。Web のあらすじは結末を書かず、公募の梗概は結末まで書く（§7）。なろうへの重複投稿は、あらすじ欄にその旨を書く [確]。
5. その投稿先への初回の書き出しで §8 の告知をする。

## 6. 字数と枚数の数え方

数え方はサイトと賞で向きが逆になる。なろうは空白・改行・ルビを除き [準]、ファンタジア大賞は空白も改行も 1 字に数える [確]。単一の「字数」は無いので、どの定義の値かを添えて告げる。

| `count_chars.py` | 数え方 | 使いどころ |
|---|---|---|
| `--mode narou` | 空白・改行・ルビ（記号もふりがなも）・傍点の記号・見出し行を除く。場面転換の記号は数える | なろうの作品文字数の定義に合わせた近似 [準]。カクヨムも同等とされる [二]。Web 連載の 1 話の長さ |
| `--mode raw` | 空白・改行も 1 字。ルビと傍点の記号、見出しの # は除く。`--with-markup` で貼る文字列そのものの長さ | 投稿上限の安全判定。空白・改行を算入する公募（ファンタジア型、GA 文庫大賞のあらすじ） |
| `--mode body` | 空白・改行・記法・見出し行・記号だけの行を除いた本文。lint の統計と同じ規約 | 章の目標字数、依頼された長さの確認、執筆中の進捗 |
| `--grid 42x34` など | 指定の字×行に流し込んだページ数。`--hang`（行末句読点のぶら下げ）、`--pair-marks`（`!?` `!!` を 1 マス）、`--assume-indent`（字下げを書き出し時に付ける原稿用） | 公募の枚数判定。グリッドは要項から転記する。`--min-pages` `--max-pages` で規定と比べる |

- ルビは全モードで数えない。なろうもファンタジア大賞も、原稿量に含めないと明言している [準][確]。
- カクヨムの正確な文字数は投稿画面のプレビュー上部で確かめる（編集画面右下は一定以上で概算表示）[確]。スクリプトの値は近似だと伝える。カクヨムのコンテストは、規定字数を一定以上超えた作品がコンテストページに出ない。基準は非公開 [確]。pixiv の数え方は [未]。
- 400 字詰換算は「総字数 ÷ 400」ではない。20 字×20 行に流し込んだ行数で数えるので、改行の余白の分だけ膨らむ。GA 文庫大賞が公表している換算から逆算すると、マス目の充填率は約 0.8、つまり総字数 ÷ 400 の 1.25 倍前後になる。会話が多いほど膨らむ。目安であって判定には使わない。
- 30 字×40 行の 1 枚 = 400 字詰 3 枚。小説現代長編新人賞が自ら使っている換算 [確]。
- 既定のグリッドは持たない。確認した 6 賞の指定は 42×34（2 賞）、40×16、40×40、30×40（1 賞は目安）で、「40 字×30 行」は 1 つも無かった。
- 判定は応募先の指定グリッドでのページ数が主、400 字詰換算は従。GA 文庫大賞は「換算枚数は目安、判定は指定書式の枚数」と明言している [確]。
- ページ換算の細則は賞ごとに違う。ファンタジア大賞は公式 Q&A で、空行も 1 行、行末の句読点はぶら下げ、`!?` `!!` は 1 字、ルビ・傍点・冒頭の題名と著者名は原稿量に含めない、と定めている [確]。スクリプトは禁則による追い出しと縦中横を再現しない近似なので、規定の境界に近いときは、ユーザーに指定書式で実際に組んで確かめてもらう。

## 7. 公募の書式を確認する手順

公募の数値はこの資料から答えない。回次も締切も半年で変わる。

1. 応募先の公式要項を取得し、取得日と URL を記録する（serial は `plan/decisions.md` に note、short は `notes.md`）。取得できなければユーザーに貼ってもらう。まとめサイトの値は使わない。
2. 要項から次を転記する: グリッド（字×行）／枚数・字数の上下限／数え方（空白・改行・ルビを数えるか）／梗概の字数と体裁、結末まで書くか／ファイル形式とファイル名の規則／1 枚目の記載事項／応募経路と締切／Web 既公開作の可否／他賞応募歴の扱い／生成 AI の規定と申告の書き場所。
3. 転記できなかった項目は空欄のまま残し、推測で埋めない。空欄がある間は「規定に適合」と報告しない。
4. Web で公開済みの作品なら、書式を整える前に適格性を見る。不可の賞なら変換せず、理由を告げる。
5. `count_chars.py` の `--grid` と `--mode raw` の両方を出し、要項の数え方に合うほうで判定する。
6. 梗概は結末まで書く。結末を伏せて問いかけで止める梗概は選考の心証を悪くする。宣伝文句は書かない。
7. §8 の告知をする。

賞ごとの違いの実例（2026-09-19 確認。転記元にせず、違いの幅を知るために見る）:

| 賞（確認した回） | 書式 | Web 既公開作 | 生成 AI |
|---|---|---|---|
| 電撃小説大賞（第 34 回） | 42 字×34 行で長編 80〜130 ページ。カクヨム応募は字数規定 | 可 | 補助的利用（誤字確認・表現の整え・アイデア出し）に限る。本文や構成の主要部分が AI 生成なら対象外。ツールと目的を本文末（Web 応募）か作品説明（カクヨム応募）に明記し、申告文は字数に入れない。制作過程の開示を求められうる |
| GA 文庫大賞（第 19 回） | 42 字×34 行で 80〜130 枚。.txt のみ。あらすじ 1,000 字は空白・改行も数える | 非商用の個人 Web・同人誌は可（投稿歴欄に記載） | 校正・ネタ出し水準のみ。使ったら備考に用法を記入。大半が AI 生成なら対象外。プロンプトの入出力をすべて開示できるようにしておく |
| ファンタジア大賞（第 40 回後期） | 40 字×16 行換算で 200〜270 枚。40 字で改行を入れない。.txt のみ。あらすじは別ファイルで結末まで | 無料公開は可（備考にサイト名と URL） | 要項・Q&A・規約のいずれにも言及なし |

| 小説現代長編新人賞（第 21 回） | 30 字×40 行で 83〜167 枚。1 枚目の記載事項は枚数に含めない | 未発表に限る。他の新人賞への応募作とその改稿も不可 | 補助的に使ったら原稿冒頭に用法を記載 |

## 8. 生成 AI 利用の申告と公募の AI 規定

2026-09-19 時点。直近 1 年で主要サイトがすべて制度化し、3 か月単位で変わっている。下表は「いま何が起きているか」を告げるための材料で、投稿の直前にユーザー自身が公式ページで確かめる前提で使う。

| 媒体 | 制度 | 義務の強さ | 本文生成に AI が関与した原稿との関係 | 確認 |
|---|---|---|---|---|

### 投稿・応募用の原稿を渡すときに告げること

投稿先ごとに、初回の書き出しで必ず告げる。礼儀ではなく適格性の問題で、誤ると投稿不可・選考対象外・受賞取消に直結する。2 回目以降は `export.py` が書き出しのたびに表示する確認の 1 行に任せ、制度が変わったと分かったときだけ言い直す。告知は 3〜4 文で足りる。中身は次の 4 点。

- 関与の事実。このスキルが書いた本文を実質そのまま使うなら、なろうでは直接使用、カクヨム・ハーメルンでは AI 本文利用に当たり、電撃・GA のように本文生成を対象外とする賞には出せない。
- 決めるのはユーザー。スキル側は、どの工程（構想・初稿・改稿・校正）に AI が関与したかを事実として整理して渡す。「AI の関与は何割」という見積もりを口にしない。割合が要るなら、版の差分と `count_chars.py` で実測する。
- 記録。電撃と GA は制作過程（ツール名・プロンプト・生成内容）の開示を求めうると明記している [確]。使用ツール・用途・日付を残すよう勧め、求められれば `plan/decisions.md` に note で残す。
- 最新の確認。申告の書き場所は賞ごとに違う（本文末、作品説明、備考欄、梗概の末尾、原稿の冒頭）。ここに書かれた内容と投稿時点の公式ページが食い違えば、公式が正しい。

AI 臭を減らす推敲は文章の質のための作業で、申告の要否を変えない。申告を避けるための言い換えや、区分を軽く見せるための助言はしない（なろうは虚偽の設定を禁止している [確]）。
