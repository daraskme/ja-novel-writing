# レビュー運用（役割・集計・盲検比較・外部モデル）

いつ読むか: 初稿に lint をかけ終えてレビュー役を立てる直前。改稿版を前の版と比べるとき。ユーザーが別のモデルや人に原稿を見せたいと言ったとき。
いつ読まないか: 設計中と執筆中。flash（レビュー役を立てない）。`roles/` の各ファイルは親が読むものではなく、サブエージェントにパスだけ渡す（理由は §2）。

## 目次

`SKILL_DIR` はこのスキルのベースディレクトリ、`PROJECT` は作品のルート。例に出てくる作品（定置網の修繕係・郁が、先代の修繕帳を借りに行く章）は書式を見せるための自作で、どの作品にも流用しない。

## 1. 誰が何を決めるか

lint は位置を出す。レビュー役は読んだ反応と診断を出す。どれを採り、どこを直すと宣言するかは親（執筆側）が決める。書いた本人のコンテキストは評価に使わない。書いたときの意図が残っていて、紙面に無いものまで読み取ってしまう。

レビュー役に頼まないことが三つある。

| 頼まないこと | なぜ | 代わりに頼むこと |
|---|---|---|
| 点数・星・総合評価 | 同系モデルの採点は甘く、点を動かすことが改稿の目的にすり替わる | 相対順位（段落は最大 3 つ、妨げなしでも最弱の 1 つ。場面は最弱の 1 つ）と引用。改稿の要否は別記 |
| 修正後の文面 | その文が原稿に貼られて声が混ざり、レビュー役の癖が入る。設定を知らない役の文面は設定も壊す | 操作で書いた方向（「L71 の最終文を消して成立するか試す」）。校閲の一意な訂正だけは文面でよい |
| 機械が書いたように見えるか | 判定が安定しない。直す方向が「人のふり」になる。読者役にその疑いを渡した時点で読み方が変わる | 読者としての反応（やめたくなった行、読み返した行、先が読めた箇所） |

lint が静かでも読者が退屈していれば失敗で、lint が騒いでも読者が先を読みたがれば成功。両者が割れたら読者の反応を採る。

ユーザー本人が点数や講評を求めたときは、求めに応じてよい（ユーザーの明示指示が上にある）。ただしその点数を、改稿の採否や打ち切りの判断には使わない。

## 2. 役割と遮断表

| 役（ファイル） | 渡す | 渡さない | 渡さない理由 | 書ける場所 |
|---|---|---|---|---|
| 執筆 `writer.md` | コンテキストパック 1 枚。改稿時は現行原稿と改稿指示書 | bible 全体、登場しない人物、レビューの生記録、lint の結果、ai-tells.md | 知っていることは書きたくなり、説明が本文に漏れる。避けたい語は見せると出やすくなる | `manuscript/` の当該章 |
| 盲検読者 `reader.md` | 原稿。連載は既読範囲のあらすじ。ジャンル読者にはジャンル名と問い 1〜2 個 | 章ビート、bible、文体シート、ジャンル契約の文面、lint、会話の経緯、書き手が誰か | 意図を知ると「伝わった」と錯覚する。約束の文面を見せると、約束が本文だけから伝わったかを測れない | `reviews/` |
| 編集 `editor.md` | 原稿、章ビート、ログライン、文体シート、`novel.toml` の `[contract]`、読者レポート | facts・state・glossary の細目、lint、ai-tells.md | 台帳を見ると校閲を始め、カタログを見ると語を数え始める | `reviews/` |
| 校閲 `proofreader.md` | 原稿、`glossary.toml`、関連する既出事実、前章末の state、lint の N・C・G・M 群の出力、文体シートの字面の欄 | 章ビート、読者レポート、bible | 意図や感想を見ると好みの指摘が混ざる。校閲が照合する相手は既出だけ | `reviews/`（検算スクリプトは `work/`） |
| 設定管理 `canon-keeper.md` | 確定原稿、章ビート、`canon/` 全部、伏線台帳、glossary、決定ログ、登場人物のシート | `reviews/`、`work/` | 採られなかった指摘や旧版の内容が「事実」に混ざる | `canon/`、`plot/foreshadowing.toml`、`style/glossary.toml`、人物シートの「変化の記録」。台帳に書くのはこの役だけ |

親が `roles/` を読まないのは、読むと親自身が読者や編集のふりを始め、別コンテキストに出す意味が薄れるからだ。

意図は委任メッセージだけでなく、履歴の継承、親の要約、プロジェクト指示ファイルの自動読込でも渡る。盲検読者は、作者との会話履歴・親の要約・設計資料を継承しない新規コンテキストで起動する。自動読込も含め継承の有無を確かめられない場合は、「盲検」と呼ばず「情報を制限したレビュー」として扱う。

## 3. 編成（モード・プロファイル別）

| 場合 | 立てる役 | 読者役への追加の問い |
|---|---|---|
| flash | なし。lint 1 回と数え上げの検算だけ | — |
| short（約 4,000 字まで） | 読者 1。編集は省く | 最終段落を外したら読後感はどう変わるか |
| short（文芸型） | 読者 1 → 編集 1 | 同上 |
| short（通俗型：感情直球が売りのもの） | ジャンル読者 1 → 編集 1。読者役をジャンル読者モードで立てる | genres.md「ジャンル読者への問い」から 1〜2 個 |
| serial・bungei | 読者 ∥ 校閲 → 編集 | なし（再話で、閉じるべき問いが閉じたかを見る） |
| serial・entertainment | 同上。第 1 話・山場・アーク末はジャンル読者を足す | ジャンル読者に、genres.md の問いから 1〜2 個 |
| serial・web | 同上 | 次話を読むか。読まないならどの行でやめたか |
| revise | 深さが「表記のみ」なら校閲だけ。「文章まで」以上は読者 1 ＋ 編集 1 | — |

- 通俗型の短編を文芸の読者に読ませない。感情の名指しや断罪の決め台詞が売りの作品を、抑制の基準で裁いてしまう。ジャンル読者モードは初読の手順（反応ログ・再話・最も弱い段落）を含むので、1 体で足りる。
- 起動コストが本文より重くなる編成は組まない。flash に読者役を立てない。web の通常話は読者 1 ＋校閲 1 で足り、編集は第 1 話・山場・ユーザーが迷っている章に回す。
- アーク末（10 章前後ごと）には、読者役に当該アークを通読させ、章を「強く動かされた順」に並べてもらう。親はそれを章ビートの `intensity` の順位と比べる。絶対値は取らない。知りたいのは、設計した山が山として読まれたか、全章が同じ熱量に均されていないかだけだ。

## 4. 委任メッセージ

汎用のサブエージェントに、役割ファイルのパスと入力のパスだけを渡す。手順や基準は役割ファイル側にあるので、メッセージに書き足さない。

```
最初に SKILL_DIR/references/roles/reader.md を読み、その指示に従ってください。
モード: 初読
対象原稿: PROJECT/manuscript/ch012.md
既読範囲のあらすじ: PROJECT/work/ch012.reader-recap.md
追加の問い: 次話を読むか
上の 2 ファイル以外、プロジェクト内のファイルを開かないでください。
出力先: PROJECT/reviews/ch012.r1.reader.md
```

役ごとに変わる行:

| 役 | モード | 入力として挙げるパス |
|---|---|---|
| reader | 初読 / ジャンル読者 / AB / 話者当て | 原稿（AB は 2 本、話者当ては台詞ファイル）、あらすじ。ジャンル読者には `ジャンル:` の 1 行と `追加の問い:` |
| editor | — | 原稿、`plot/beats/chNNN.toml`、`plan/logline.md`、`style/style-sheet.md`、`novel.toml`、読者レポート。短編は原稿、`notes.md`、読者レポート |
| proofreader | — | 原稿、`style/glossary.toml`、`work/chNNN.facts.md`（関連する既出事実の抜粋）、`canon/state/ch（N-1）.md`、`work/chNNN.lint.txt`、文体シート |
| writer | 初稿 / 改稿 | `work/chNNN.pack.md`（短編は `notes.md` と既稿の末尾）。改稿は原稿と `reviews/chNNN.rK.brief.md` も。読む scene-cards のカード名を 2〜4 枚 |
| canon-keeper | 更新 / 承認反映 | 確定原稿、章ビート。承認反映は confirmed にする事実 ID の一覧 |

- 既読範囲のあらすじは、`canon/summaries/` の既出の章要約から親が作る。章ビートや bible から作らない（未出の情報が混ざる）。第 1 章と短編には要らない。
- 校閲に渡す `work/chNNN.facts.md` は、`canon/facts.jsonl` を登場人物 ID で絞った抜粋（proposed も含める）。`work/chNNN.lint.txt` は `novel_lint.py` を N・C・G・M 群に絞って（`--only`）実行した出力の保存。統計や語彙密度の警報は校閲に渡さない。fix / keep を決めるのは親だ。
- ジャンル読者に渡すのは、ジャンルの呼び名（読者が題名やタグから知りうる語。「ざまぁ短編」「日常の謎」）と、genres.md「ジャンル読者への問い」から選んだ 1〜2 問。`[contract]` の promise の文面、結末、仕掛けは渡さない。
- サブエージェントがファイルに書けない種類なら、返答を親が `reviews/` に保存する。要約せず全文を保存する。
- 並列: 読者と校閲は同時に出してよい。編集は読者レポートを入力にするので後。ジャンル読者は読者と同時。

## 5. 各役から返ってくるもの

**盲検読者**
1. 反応ログ。行番号と 15 字以内の引用つきで、やめたくなった行／読み返した行（分からなくて・良くて）／先が読めた箇所／誰の台詞か迷った箇所／説明されたと感じた行／取って付けたと感じた行。反応が無かった段落については何も書かれない。
2. 再話。本文を見返さずに 200 字程度で、何が起きたか、誰が何を望んでいるか、次に何が起きると思うか、いちばん残った一文。
3. 最も弱い段落を最大 3 つ、弱い順に。読む妨げが無ければ「妨げなし」でよいが、最弱の 1 つは挙げる。弱さと改稿の要否は理由つきで別記する。
4. 理解できたかと、面白かったか・心に残ったかを分けた記録。
5. 追加の問いへの答え（あれば）。

点数、修正文、総評、書き手の推測は含まれない。含まれていたら集計でそこだけ捨てる。

**編集**: 冒頭で読み続けるかどうかと理由、最弱の場面 1 つ、§6 の書式の指摘が最大 5 件、守りたい箇所の候補 2〜3 点。方向だけで文面は無い。

**校閲**: §6 の書式で、表記・既出との矛盾・状態の連続・知識状態・呼称・世界制約・数え上げ。矛盾は「本文の引用」と「既出事実 ID か state の行」の対で示される。機械的に一意な訂正は修正後の文字列つき。

## 6. 指摘の書式と重大度

役にも、モデルにも、人にも依らない共通の書式。外部から持ち込まれた指摘もこの形に写してから裁く。

```
### E02 [S2] L60-66
引用: 「ほんなら、持っていかれ」
問題: 登志子が帳面を貸す気になった理由が紙面に無い。読者は理由を補えず、都合で動いたように読む
根拠: 読者レポートの再話に「なぜか貸してくれた」
方向: 説得の台詞を足すのでなく、郁が先に何かを差し出す行為を決め手にする
```

ID は役の頭文字（R 読者・E 編集・P 校閲・X 外部）＋連番。根拠は、本文の別の箇所、読者の反応、既出事実 ID、章ビートの項目、検算結果のどれか。校閲は「方向」の代わりに「訂正」（一意に決まる修正後の文字列）を書く。行番号は原稿ファイルの行（1 段落 1 行なので段落番号と同じ）。版が変わるとずれるので、位置の正本は引用のほうだ。

| 重大度 | 何か | 扱い |
|---|---|---|
| S1 | 読者が筋を追えない。既出との矛盾。視点の破れ。章ビートの intent・direction やジャンル契約に反する。投稿先の規定違反。数え上げの不一致 | 必ず直す |
| S2 | 場面の目的が見えない。動機が飲み込めない。声が人物と合わない。説明の塊。`reader_should` の未達 | 直す。ただし 1 周に触る箇所の枠内で |
| S3 | 反復、リズム、語の選択 | 1 段落の中で済むものだけ |
| S4 | 好みが分かれる | 直さない。backlog に記録だけ |

重大度を最終的に付けるのは親。レビュー役が付けた重大度は提案として読む。

## 7. 集計して改稿指示書にする

1. **引用を原稿に当てる。** 各指摘の引用を Grep で探し、原稿に無い引用の指摘は捨てる。レビュー役は、内部でも外部でも、読んだ気になった文を引用として書くことがある。
2. **根拠の無い指摘を捨てる。** 引用も読者反応も事実 ID も伴わない「全体に描写が薄い」の類。
3. **契約に当てる。** ジャンル契約の `keep`、文体シートの例外宣言に当たる指摘は S4 に落とす（`emotion_naming = "direct"` の作品で感情の名指しを咎める指摘、`chapter_hook = "off"` の作品に引きを求める指摘）。
4. **読者の再話を `reader_should` と突き合わせる。** 短い再話の省略を即「未伝達」にしない。重要な欠落は、意図を教えない追加質問（「その時点で郁が知っていたことは何か」など）で確かめる。理解できたかと、面白かったか・心に残ったかは別に記録し、理解済みでも退屈という反応は残す。
5. **重ねる。** 同じ行・同じ現象を複数の役が別々に挙げていたら最優先。読者がやめたくなった行と編集の最弱場面が重なれば、そこが今回の中心になる。単独の指摘は重大度で採否を決める。
6. **採る方向を設定に当てる（省かない）。** レビュー役は設定の全体を知らずに提案する。採る予定の方向ごとに、コンテキストパック、前章末の state、関連する既出事実、呼称表、世界制約に当てて問う。その人物はその時点でそれを持っているか。知っているか。その場にいるか。その語はこの世界にあるか。声シートの話し方で言える内容か。
   例: 編集の E02 は、方向の末尾に「先代の形見の網針を差し出す、など」と具体物を添えてきた。state/ch011 では、網針は ch010 で親方の辰巳に預けたままになっている。郁は持っていない。方向を「何を差し出すかは、パックにある郁の持ち物から執筆側が選ぶ」に書き換えて採る。矛盾する方向をそのまま執筆役に渡すと、執筆役は指示を優先して既出を壊す。
7. **守る長所を 2〜3 点決める**（声が売り物の bungei は 5 点まで）。読者の「読み返した行（良くて）」「いちばん残った一文」を優先し、無ければ編集の候補から。ユーザーが触るなと言った文と決め台詞は数に入れず無条件で守る。決めずに改稿へ出すと、良かった破調が真っ先に均される。
8. **改稿指示書を書く。** 600 字以内、直す箇所は最大 5、方向だけ、守る長所つき。short は最弱の場面 1 つに絞る。執筆役に渡すのはこの 1 枚で、生のレビューは渡さない。生の記録は件数が多く、互いに食い違い、採らなかった指摘まで反映されてしまう。ユーザーが生の記録を見たいと言えば、そのまま見せてよい。
9. **残りを `reviews/backlog.md` へ。** S4 と、枠から溢れた S2・S3。ユーザーへの報告には S2 以上だけ載せる。

指摘が一つの場面の過半に及び、しかも視点の破れやビートの要約消化のような構造の問題なら、差分で繕わず場面単位で書き直す（手順は revision.md）。

改稿指示書の例:

```
# ch012 改稿指示書 r1

守る（触らない）
- L41「もう濡れてもいない盆だった。」読者・編集とも読み返した行に挙げた
- L52-57 郁が干し柿のへたを外すあいだのやりとり。台詞だけで二人が聞き分けられる
- 章末 L88 車内灯の下で切り口を見るところで終わること

直す（この 4 か所のほかは一字も動かさない）
1. [S1] L23 郁が登志子を「奥さん」と呼んでいる。ch009 で「登志子さん」に変わった（ch009-07）。戻す
2. [S2] L30-36 帳面の来歴を登志子が一息に話す。読者がやめたくなった箇所。この章で要るのは「三月が無い」に効く分だけ。残りは削るか、郁が訊いて登志子が答えない形に割る
3. [S2] L60-66 登志子が貸す気になった理由が伝わっていない（再話に「なぜか貸してくれた」）。登志子が応じる利害や価値観を本文で示す。郁の言葉か行為がその条件に届くようにし、物を使うならパックの持ち物から選ぶ
4. [S3] L71 の最終文を消し、その前の台詞で段落を終えられるか試す

見送り: L15 の喩え（S4、backlog）
```

## 8. 声の識別テスト

serial で 5 章に 1 回ほど、short は 3 人以上が話す作品だけ。人物の声が混ざってきたと感じたときにも使う。

1. 本文から台詞を 10〜15 本、話者が偏らないように抜く。内容で話者が割れる台詞（名乗り、職業の話、相手への呼びかけ）は外すか、固有名詞を伏せ字にする。
2. 人物ごとに見本を 2 本ずつ、別の確定章から取って A・B・C のラベルで示す（声シートの見本台詞を使ってもよい。その場合は「本文が声シートの声で書けているか」の検査になる）。
3. 同じ台詞で語尾マスク版も作る。一人称、終助詞、語尾の役割語を「＿」に置き換える。
4. `reader.md` の話者当てモードに、原文版と語尾マスク版を別々のサブエージェントで解かせる（同じ個体に両方見せると答えが漏れる）。
5. 読み方: 原文版の正答が 7 割に届かなければ声の設計不足。原文版は当たるのに語尾マスク版で大きく落ちるなら、語尾だけで書き分けている。どちらも character.md の声シート（語彙の層、文の長さ、敬語段階、問いへの応じ方）に戻って直す。取り違えられた台詞に装飾的な発話タグを足して済ませない。

## 9. 盲検 A/B

改稿は前の版に勝って初めて採用する。LLM の改稿は、指摘を全部反映した結果、角が取れて平らになることが多い。

1. 改稿に入る前に、現行版を `work/ch012.r1.md` として複製しておく（r1 は 1 周目のレビューにかけた版。2 周目の前は r2）。git の履歴があればそこから取り出してもよい。
2. 比較前に、今回改善したい読者体験を一つ決める。途中の章は継続意欲、最終章や完結掌編は結末の受け止め、喜劇は笑いの成立など、対象に合う問いを選ぶ。比べる 2 版を `work/ab/ch012.X.md` と `Y.md` に複製する。どちらを X にするかは `python -c "import random;print(random.choice('XY'))"` で決める。親が決めると「新版を後に置く」癖が出る。対応表は判定が返ってから `reviews/ch012.ab.md` に書く。
3. `reader.md` の AB モードで、§2 の遮断を満たす新規コンテキストに渡す。初読レビューをした個体は使わない。問うのは、選んだ読者体験にどちらがより届いたか。版の由来を伏せ、理由は両版の本文の引用で求める。どちらが改稿版かは推測させない。
4. 新版が選ばれたら採用。旧版が選ばれた、または差がないと返ったら、旧版に戻して改稿を終える。
5. 戻すときも、S1 の訂正（既出との矛盾、表記の FAIL、数え上げ）は旧版に差分で入れ直す。比較にかけているのは読者体験に関わる改稿であって、誤りの訂正ではない。
6. 判定の理由に挙がった引用が、2 版で同一の箇所ばかりなら、その判定は雑音として「差がない」に数える。

頻度: 第 1 話・山場・最終章は各周。serial の通常章と short は、初稿と最終版で 1 回。S1 の訂正しかしていないなら省く（読者体験の差を比べる対象が無い）。flash は行わない。毎周やらないのは起動コストとの釣り合いで、1 回にした分、見逃す劣化は増える。声が売り物の bungei で 2 周した章は、各周で比べるほうが安全だ。

同系のモデルは、より整った版を「自然」と感じて選びやすい。第 1 話、山場、応募前の最終稿では、同じ 2 ファイルを §12 の外部モデルかユーザー本人にも見てもらう。

## 10. 打ち切り

周回の上限: flash 1／short 2／serial の通常章 2、第 1 話・山場・最終章 3。ユーザーが別の上限を指定していればそちら。

次のどれかで止める。
- 盲検 A/B で新版が勝てなかった（旧版へ戻す）
- S1 が 0、S2 が 1 以下になった
- 新しく出た指摘がすべて S3 以下
- 同じ箇所の往復（1 周目で A→B、2 周目で B→A を求める指摘）。好みの領域に入った印
- 同じ段落が 2 周続けて無変更。以後その段落は対象から外す
- 同じ種類の直し（語の入れ替え、順序の入れ替え）を 2 周して改善が無い。3 周目に同種を重ねず、構造の診断に戻るか巻き戻す
- 上限に達した。残件は backlog へ

2 周目以降は削る改稿を優先する。LLM の改稿は足す方向に偏る。

## 11. サブエージェントが使えないとき

親が役を順に演じるしかない。意図を知っている読者は盲検ではないので、効果は落ちる。落ち幅を小さくする手順:

1. 執筆と評価のあいだに別の作業（lint、字数の実測、台帳の下準備）を挟み、原稿はファイルから Read し直す。記憶の中の原稿を評価しない。
2. 役割ファイルは、その役を演じる直前にだけ読む。読者→校閲→編集の順。役ごとに出力をファイルへ保存してから次へ進む。
3. 読者役は問いを変える。再話は意図を知っていれば書けてしまう。代わりに `reader_should` の項目ごとに「それを読者に伝えている文を行番号で指す」。指せない項目が未達。指せた文が 1 つだけで、それが説明文なら弱い。
4. 最も弱い段落は §4 と同じく最大 3 つ、妨げなしでも 1 つ。弱さと改稿の要否は別記する。
5. 盲検 A/B は成り立たない。変えた箇所を 2 版並べてユーザーに選んでもらうか、§12 の外部モデルを使う。どちらも無理なら、両版をファイルから読み直して変更箇所だけを並べ、「どちらが具体的か、どちらがこの人物に固有か」で決める。自分の改稿には甘くなるので、この場合は改稿を S1・S2 と削る改稿に限り、周回は 1 回にする。
6. 成果報告に「レビューは同一コンテキストで実施」と 1 行書く。

## 12. 外部モデルへの持ち出し

同系のモデルは癖の分布が同じなので、互いの最頻値を「自然」と感じて見逃す。別系統のモデルには、こちらの最頻値が目立って見える。手間に対して得るものが大きいのは、第 1 話、山場、応募前の最終稿、盲検 A/B の判定。

**同意。** 原稿が別の事業者に送られる。ユーザーが求めたとき、または提案して同意を得たときだけ行う。未発表作や応募予定作では、送る前にもう一度確かめる。

**手順（Codex CLI の例）**

1. 見せる物だけを入れたフォルダを作る。§2 の履歴継承と自動読込の条件も確認する。
   ```
   PROJECT/work/ext/ch012/
   ├── request.md      下の依頼文
   ├── manuscript.md   原稿の複製
   └── recap.md        連載のみ。既読範囲のあらすじ
   ```
   章ビート、bible、lint の結果、内部レビューは入れない。整合を見てもらうときだけ `facts.md`（関連する既出事実の抜粋）を足す。
2. 読み取り専用で、そのフォルダを作業ルートにして実行する。
   ```
   codex exec -s read-only --skip-git-repo-check -C "PROJECT/work/ext/ch012" -o "PROJECT/reviews/ch012.r1.ext-codex.md" - < "PROJECT/work/ext/ch012/request.md"
   ```
   - Bash の例。長い依頼文はファイルから標準入力へ渡し、末尾の `-` で読む。`-s read-only` はモデル側の書き込みを制限し、`-o` は CLI 自身が最終返答を保存する指定。パスは起動元から解決できるものを使う。
   - フラグは CLI の版で変わる。初回は `codex exec --help` で上の指定が使えるか確かめ、無いものは同じ働きの指定に置き換える。
   - 読み取りはフォルダ外にも届きうる。持ち出し先はプロジェクト外の一時ディレクトリも選べるが、それだけで盲検は保証しない。指示ファイルの自動読込も確認し、不明なら情報を制限したレビューと記録する。
   - PowerShell では UTF-8 の `Get-Content -Raw -Encoding utf8 request.md` を、末尾に `-` を付けた同じコマンドへパイプする。標準入力へ送る文字コードも UTF-8 に揃える。
   - Bash ツールのタイムアウトは長め（10 分）に取る。
3. モデル名は指定しない（ユーザーの既定に従う）。ユーザーがモデルを指定したら `-m` で渡す。
4. 失敗（タイムアウト、非ゼロ終了、空の返答、拒否）は、どのコマンドで何が起きたかをユーザーに伝えて指示を待つ。黙って再実行しない。別のモデルに勝手に切り替えない。失敗を無かったことにして集計しない。
5. 他の CLI でも形は同じ。読み取り専用、作業ルートを持ち出しフォルダに限定、最終返答をファイルへ。CLI が無ければ、ユーザーが `request.md` と原稿をチャット画面に貼り、返答を `reviews/ch012.r1.ext-manual.md` に保存してもらう。

**依頼文（request.md）の型**。読者として読んでもらう場合の型で、`{ }` は場合によって入れる行。スキルの `assets/templates/external-review-request.md` は役割（読者・編集者・校閲者）を選べる汎用の雛形で、編集者や校閲者として頼むときはそちらを埋める。どちらを使っても、渡す物の絞り方と、返答の裁き方は変わらない。

```
# 原稿を読んでください

あなたは日本語の小説を読み慣れた読者です。同じフォルダの manuscript.md を頭から通して読み、下の形式で答えてください。このフォルダの外のファイルは開かないでください。
{先に recap.md（ここまでのあらすじ）を読んでください。}
{ジャンル: …（題名やタグから読者が知りうる呼び名だけ）}

## 答えてほしいこと
1. 読みながらの反応。該当する行だけ、行番号と 15 字以内の引用を付けて（行番号が分からなければ引用だけで構いません）。
   読むのをやめたくなった行／読み返した行（分からなくて・良くて）／先が読めた箇所／誰の台詞か迷った箇所／説明されていると感じた行
2. 再話。本文を見返さずに 200 字程度で。何が起きたか、誰が何を望んでいるか、次に何が起きると思うか。
3. 最も弱い段落を最大 3 つ、弱い順に。読む妨げが無ければ「妨げなし」でよいですが、最弱の 1 つは挙げてください。行番号と反応、改稿の要否と理由は別記してください。
4. 理解できたこと・分からなかったことと、面白かったこと・心に残ったことを分けて。
5. 辻褄の合わない箇所（時刻、人数、持ち物、誰が何を知っているか、字数や個数を言っている表現）。食い違う 2 か所を両方引用して。

## 書かないでほしいこと
- 点数、星、総合評価
- 書き直した文章や代わりの台詞。直す方向は「L30-36 は半分にできる」のように操作で
- 書き手についての推測
- 全体への褒め言葉。良かった箇所は 1 の「読み返した行（良くて）」に引用で

引用は本文のとおりに。本文に無い文を引用しないでください。
```

A/B を頼むときは、`X.md` と `Y.md` を入れ、比較前に改善したい読者体験を一つ選ぶ。問いを「今回の体験にどちらがより届いたか。理由を両方からの引用で。どちらが先に書かれたかは推測しない」に差し替える。

**返答を指摘の書式に写す**

| 返答によくあるもの | 扱い |
|---|---|
| 点数、総評、褒め言葉 | 捨てる |
| 書き直した文面 | 文面は捨て、何をしようとした直しかを方向に訳す（「台詞を短くし、理由を言わせない」）。訳せないものは捨てる |
| 本文に無い引用 | Grep で当てて、無ければ指摘ごと捨てる |
| 「優先度: 高」などの自己申告 | 見ない。§6 の基準で親が付け直す |
| 設定を知らない提案 | §7-6 の照合にかける。外部の提案は設定との矛盾がいちばん多い |
| 機械が書いたかどうかの言及 | 捨てる。その指摘が指している行に、読者として止まる理由があるかだけを見る |

写した指摘は ID を `X01…` とし、§7 の集計に内部の指摘と同列で入れる。内部の役と重なった指摘は優先度が上がる。外部だけの指摘は、外部だからという理由では上げも下げもしない。生の返答は `reviews/` に残す。

## 13. ファイルの置き場

```
reviews/ch012.r1.reader.md      読者（ジャンル読者は .genre.md）
reviews/ch012.r1.editor.md      編集
reviews/ch012.r1.proof.md       校閲
reviews/ch012.r1.ext-codex.md   外部の生の返答
reviews/ch012.r1.brief.md       改稿指示書（執筆役に渡すのはこれだけ）
reviews/ch012.ab.md             A/B の対応表と判定
reviews/backlog.md              見送った指摘
work/ch012.r1.md                1 周目のレビューにかけた版（改稿前の複製）
work/ab/  work/ext/             比較用・持ち出し用の複製
```

`r1` は周回。short は章番号を省く（`reviews/r1.reader.md`）。`reviews/` は残す。なぜそう直したかの記録になり、同じ指摘の往復を見つける材料になる。
