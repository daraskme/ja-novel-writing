ファイルは変更していません。書き込みを伴わない既存テスト101件は通過。追加サンプルはメモリ上と標準入力で検査しました。全件の再実行、Python 3.11 以上でのプロジェクト統合検証はしていません。

### 5. C 群の FAIL を、確実に誤りといえる範囲へ狭める

**重大度: high**  
**対象:** [scripts/novel_lint.py:54](scripts/novel_lint.py:54)、同 `155–160,733–788`

**問題・根拠:** 以下を実行で再現しました。

| 入力 | 現在の結果 | 問題 |
|---|---|---|
| `「ありがとう」は四文字ではなく五文字だ。` | C01 FAIL | 否定された数を断定として検査 |
| `「いすゞ」の三文字。` | C01 FAIL | `ゞ` を落として二文字と数える |
| `「𠮷野家」の三文字。` | C01 WARN | 拡張漢字を落として二文字と数える |
| `「どこ？」`＋改行＋`たった三文字の返事を待った。` | C01 FAIL | 質問と、待っている返事を同一視 |
| `「あぁ」は二拍で、母音を長く延ばす。` | C03 FAIL | 小書き母音を無条件に除外 |
| `四音の言葉、「しゃしん」。` | C 群の指摘なし | 音数の逆順構文を検査しない |
| `「｜今日《きょう》」は三音。` | 漢字なので数えられないと WARN | 利用できる読みを先に捨てている |

「FAIL は必ず直す」という運用なので、誤検出は正しい本文を壊します。

**修正案:**

- 否定・訂正・引用・文境界をまたぐ対応づけは、FAIL にしない。
- 字種の固定範囲をやめ、正規化した Unicode の文字カテゴリで数える。解釈できない字を黙って落とさない。
- 拍数は小書き仮名の結合を解析する。発音が曖昧な表記は WARN。
- ルビを保持した解析と、字数用の親文字解析を分ける。
- `音` を常にモーラと決めつけない。例えば「子音と母音からなる二音」は別の数え方です。

字数部分の修正の核は、例えば次です。

```python
s = unicodedata.normalize("NFC", strip_notation(x))
count = sum(unicodedata.category(c)[0] in {"L", "N"} for c in s)
```

これだけで全文脈判定は解決しませんが、`ゞ` や `𠮷` を落とす不具合は避けられます。

**対象:** `references/prose-core.md:284`

**問題・根拠:**  
曖昧な返事を「湿気を吸った床を踏んだときの手応えのなさ」へ結びつけています。「手応え」は比喩的には使えますが、ここでは踏む感覚との接続も、湿った床の性状も曖昧です。「畳屋だから畳の比喩」を優先した印象が残ります。

**修正案:**

> 値段を言うと、奥さんは「はあ」と言った。梁瀬は見本を片づけかけた手を止めた。  
> 「安い表もあります。そちらも見ますか」

比喩を成立させる材料がない場合の、比喩なしの良い例にする方が有効です。

### 2-4. 騒音の再解釈が、都合のよい善意による回収になっている

**重大度: medium**  
**対象:** `references/structure.md:89–94`

**問題・根拠:**  
三年間話さなかった相手の深夜の洗濯が、最後の説明一つで救済的な善意へ変わります。さらに主人公が新居で空の洗濯機を回すため、「嫌だったものを愛着へ反転する」きれいな回収が二重です。構成例として模倣すると、事情の説明だけで感情を解決する型が増えます。

**修正案:** 意味の変化を、善人認定や和解と分ける。

> 転: 男は「帰ってくるのが、あの時間で」と言う。彼女は初めて、洗濯が終わったあとにも男の一日が続いていたことを考える。  
> 結: 「でも、うるさかったです」と彼女は言う。男は段ボールを抱え直し、「すみません」と答える。

理解と不満を両方残せます。

### 2-5. 戦闘例は、位置関係より動詞の勢いが先に立っている

**重大度: medium**  
**対象:** `references/scene-cards.md:148–149`

**問題・根拠:**  
拳が箱を割る→腕が肘まで氷水に入る→抜く動きが止まる→下段を蹴る→五段の中身が背中へ落ちる、という連鎖で、箱の高さ、蓋、腕が止まる理由、崩れる向きが不足しています。具体語が多いことと、動きが追えることを混同しています。

**修正案:** 動作を減らし、原因を見えるようにする。

> 男が踏み込んだ。志摩は箱の山に沿って横へ逃げた。拳が最上段の角を砕き、氷水が床へこぼれる。男が追おうとして足を滑らせた隙に、志摩は通路へ抜けた。

肩の負傷を残すなら、肩へどのように当たったかを別に明示する。

## 観点3 — 日本語・作法・投稿仕様

### 3-1. タ形／ル形の表を、機能の対応表として断定しすぎている

**重大度: medium**  
**対象:** `references/prose-core.md:60–65,79`

**問題・根拠:**  
「出来事＝タ形」「ル形にすると出来事が足踏みする」は一般則になりません。79行で一部例外を認めていますが、先の表と説明が強すぎます。

歴史的現在形は過去の出来事を語る手段で、物語の骨格をなす節にも現れます。[小玉安恵「体験談における歴史的現在形の機能と視点」](https://www.jstage.jst.go.jp/article/nihongokyoiku/148/0/148_114/_article/-char/ja/)

**修正案:**

> タ形・ル形・テイル形は、出来事の種類だけでなく、語りの時点、知覚への近さ、前後との関係で選ぶ。出来事をル形で進める語りもある。文末の種類を散らすためだけの変更を避ける。

### 3-2. ノベルアップ＋の操作説明が内部で矛盾している

**重大度: medium**  
**対象:** `references/notation.md:155,160`

**問題・根拠:**

**修正案:**

> ハーメルンは対応範囲内の記法をそのまま貼る。ノベルアップ＋は `--to kakuyomu` の出力を貼り、傍点はエディタの置換操作を行ってプレビューで確認する。

公式仕様の再確認時には、この二つを別項目で確認する。

### 3-3. `[確]` に確認先がなく、仕様更新を追えない

**重大度: medium**  
**対象:** `references/notation.md:6–16,145–155`

**問題・根拠:**  
確認日と確度はありますが、個々の主張に公式URLがありません。記法の上限、利用できる欄、エディタの補助機能が同じ行へ詰め込まれており、一部変更時の追跡が困難です。

**修正案:** 項目ごとに `source / checked_at / scope` を付ける。例えば、

> カクヨムのルビ・傍点: 公式「ルビや傍点を付けるには」を参照。確認対象は記法、文字数上限、利用可能な欄。[公式ヘルプ](https://kakuyomu.jp/help/entry/notation)

なろうの字数上限も別の出典として保持する。[公式「ルビ挿入」](https://syosetu.com/helpcenter/helppage/helppageid/42)

## 観点5 — scripts の不具合

### 5-1. 本文・台詞の分解が、正当な本文を消している

**重大度: high**  
**対象:** `scripts/novel_lint.py:255–285,849`

**問題・根拠:** 実行結果は次のとおりです。

- `「……」` → 本文0字、M01 FAIL。
- `『今日は帰りません』` → 台詞0字、全文を地の文扱い。
- 改行を含む `「今日は\n帰りません」` → 台詞0字。

最初は正当な無言の台詞です。後二つは採用する括弧や内部記法次第ですが、非対応ならそう報告すべきで、統計へ黙って混ぜるべきではありません。

**修正案:**

> 日本語文字の有無で本文を捨てない。本文行の分類は count/export と共有する。台詞は括弧の開始・終了を追跡する。非対応形式は入力形式の警告にし、その箇所の台詞統計を確定値として扱わない。

真に空の入力は実行エラー2にするなど、M01 FAIL と「FAIL はN/Cだけ」の不一致も解消する。

### 5-2. 表記の FAIL が、文書の規則・例外と一致しない

**重大度: high**  
**対象:** `references/notation.md:97,130`、`scripts/novel_lint.py:351–369,375–392`

**問題・根拠:**

- 半角字下げは FAIL と記載されるが、実行では N05 INFO。
- 全角空白二つの字下げは N05 が出ない。
- 字下げなしの entertainment 原稿も、プロジェクト指定なしでは INFO。
- `。」` を作者の流儀として保持すると文書にあるが、実装は常に FAIL。
- N03 は全角一つを要求しながら、正規表現では半角空白・タブも通す。

**修正案:**

> N 群は作品の表記契約との不一致を判定する。設定のない既存原稿は流儀を推定して確認対象とし、直ちに標準化しない。

設定例:

```toml
[format]
indent = "fullwidth"
dialogue_period = "keep"
after_exclamation = "fullwidth"
```

字下げは `startswith("　")` ではなく、行頭空白列全体を検査する。

### 5-3. 密度の最低標本量を、分母と違う量で判定している

**重大度: medium**  
**対象:** `scripts/novel_lint.py:646,668–676`

**問題・根拠:**  
地の文12字に感情語3回、台詞800字の入力で、K08 が「地の文1000字あたり250回」と WARN になります。全文は十分長くても、計測対象の地の文は短すぎます。

**修正案:**

```python
lines, base = ...  # ルールの unit に対応する値
if base < cfg.guards["density_min_chars"]:
    # このルールは回数のみ報告
    continue
```

全文用の指標と地の文用の指標で、ガードを別々に適用する。

### 5-4. 「近い範囲の反復」を全文平均で判定している

**重大度: medium**  
**対象:** `scripts/novel_lint.py:678–687`

**問題・根拠:**  
冒頭の「そっと」3回は警告されますが、後ろに無関係な文章を足すと同じ集中が警告されなくなりました。`repeat_window` を窓として走査せず、全文長で必要回数を引き上げているためです。

**修正案:**

> 語ごとの出現文字位置を保持し、`repeat_window` 内に `repeat_warn` 回以上ある区間を検出する。原稿の末尾への追記で、既存区間の反復警告を消さない。

### 5-5. 自動較正で `direct` 契約の例外が解除される

**重大度: high**  
**対象:** `scripts/novel_lint.py:229–235`、`scripts/calibrate.py:36–44,108–117`

**問題・根拠:**  
`emotion_naming="direct"` の K08 は通常 off ですが、override が一つでもあると off になりません。較正処理は K08 も測り、override を生成します。

設定オブジェクトで、較正値相当の override を追加すると、`{'off': True}` から数値閾値へ戻ることを確認しました。

**修正案:**

```python
if self.emotion_naming == "direct" and rule_id == "K08":
    if not (isinstance(ov, dict) and ov.get("enable") is True):
        return {"off": True}
```

較正側も off のルールを除外する。機械的な再計算に、契約を変更する権限を与えない。

### 5-6. 文末分類を、文法的な分類として使えない

**重大度: medium**  
**対象:** `scripts/novel_lint.py:83–99`

**問題・根拠:**  
`そうなんだ。`、`嫌いだ。`、`あした。` がすべて `ta` になります。文字列末尾の判定を、タ形の比率として報告しているためです。

**修正案:**

> 確信できる活用だけを分類し、曖昧な末尾は unknown にする。簡易実装を維持するなら、表示名を「表面上の末尾パターン」に変更し、文法的なタ形率とは呼ばない。

分類変更後は、その分類に依存する較正値も測り直す必要があります。

### 5-7. `--length` が検査を変えない

**重大度: medium**  
**対象:** `scripts/novel_lint.py:179–184,972,1024`、`references/style-sheet.md:195`

**問題・根拠:**  
`length` は保持・出力されますが、検査分岐には使われません。文書の掌編向け運用を期待して `--length flash` を指定しても、通常と同じ密度検査が動きます。

**修正案:** どちらかに統一する。

> `--length` は出力用の属性で、検査内容を変えない。

または、長さ別のガードを `thresholds.json` に定義し、実際に参照する。

### 5-8. C 群の通過を、広い意味の検算完了と誤解させる

**重大度: medium**  
**対象:** `SKILL.md:23`、`references/ai-tells.md:462–463`、`scripts/novel_lint.py:831–841`

**問題・根拠:**  
画数、回文、年齢、日付、曜日まで検算対象に掲げていますが、実装の多くはキーワードの案内です。`二〇二六年二月三十日、月曜日。` は C 群に何も出ません。

**修正案:**

> C01/C03 は対応構文の字数・拍数を検査する。C05–C07 は検算対象の案内であり、検算済みを意味しない。日付・年齢・曜日・画数・文字遊びは別途検証する。C 群の警告なしを、これらの正しさの根拠にしない。

なお、今回の標準入力検査では、正しい字数／誤った字数／不正UTF-8の終了コードは **0／1／2** でした。UTF-8 BOM・CRLF付きの入力も通っています。この範囲では不具合を認めません。

## 観点6 — スキルとしての設計

### 6-1. プロジェクトの存在が、ユーザーの作業意図を上書きする

**重大度: medium**  
**対象:** `SKILL.md:8–10,37–42`

**問題・根拠:**  
`novel.toml` があれば必ず serial なので、そのプロジェクトでの講評・文体相談・部分校正まで章執筆へ分類されます。「小説以外には使わない」と、ファイル存在による強制起動も衝突します。

**修正案:**

> まず依頼を執筆・推敲・相談・文体分析に分類する。`novel.toml` の有無は、既存設定を参照するかを決める条件とする。長編プロジェクト内でも revise / consult を選べる。

description から「存在すれば必ず使う」を外す。

### 6-2. 深さが明示済みでも確認を求める

**重大度: medium**  
**対象:** `SKILL.md:91`、`evals/evals.json` の `revise-ai-smell`

**問題・根拠:**  
本体は必ず一問聞く手順、eval は「文章レベル指定済みなので聞かない」を期待しています。

**修正案:**

> 修正の深さが依頼から分かる場合は、その範囲で進める。不明な場合だけ一問聞く。「文章レベルで直して」は文章の修正までの許可とする。

### 6-3. 「盲検が破れる経路は委任メッセージしかない」は誤り

**重大度: high**  
**対象:** `references/review-protocol.md:51`、`SKILL.md:141–147`

**問題・根拠:**  
履歴の継承、親の要約、プロジェクトの自動読込などでも意図が渡ります。ファイル読取制限だけでは、既に持っている情報を消せません。

**修正案:**

> 盲検読者は、作者との会話履歴・親の要約・設計資料を継承しない新規コンテキストで起動する。継承の有無を確認できない場合は「盲検」と呼ばず、情報を制限したレビューとして扱う。

### 6-4. 再話に出ないことを、伝わっていないことと同一視している

**重大度: medium**  
**対象:** `references/roles/reader.md:37`、`references/review-protocol.md:142`

**問題・根拠:**  
200字程度の再話には省略が生じます。そこにない `reader_should` をすべて未伝達とすると、理解済みの情報を説明し直す改稿へ向かいます。

**修正案:**

> 再話との差分は確認候補とする。重要な欠落には、意図を教えない追加質問で理解を確認する。理解できたかと、面白かったか・心に残ったかは別に記録する。

### 6-5. A/B の問いが、最終章や完結掌編に合わない

**重大度: medium**  
**対象:** `references/review-protocol.md:187–192`

**問題・根拠:**  
最終章でも「どちらを読み続けたいか」だけで比較します。完結の充足、笑いの着地、語りの声を評価したい場面で、未解決の多い版が有利になり得ます。

**修正案:**

> 比較前に今回改善する読者体験を一つ決める。途中章は継続意欲、最終章は結末の受け止め、喜劇は笑いの成立など、対象に合う問いを使う。由来を伏せ、理由は本文の引用で求める。

旧版へ戻す原則は維持してよいです。

## 観点7 — 説明文そのもの

### 7-1. 操作に不要な原因説明を、確定したモデル理論として書いている

**重大度: medium**  
**対象:** `SKILL.md:15`、`references/ai-tells.md:139,460`

**問題・根拠:**  
「親切さの漏出」「否定対比は英語の転写」「文字を一字ずつ見ていないから数えられない」は、観測できる現象と原因仮説が混ざっています。原因を断定しなくても、編集操作は説明できます。

**修正案:**

> 直前の内容を説明し直す文が続いたら、追加情報があるか確認する。  
> 否定対比では、否定される側の見方が本文に存在するか確認する。  
> LLM の字数・音数の申告は誤ることがあるため、外部計算で検算する。

作用する指示だけを残し、モデルの内面を擬人化した説明を減らすべきです。

### 7-2. 「なぜ」と例文解説が、同じ規則を繰り返している

**重大度: low**  
**対象:** `references/prose-core.md:32–46,239–269`、`references/roles/writer.md:50–59`

**問題・根拠:**  
既定→なぜ→悪い例→良い例→良い理由→診断→例外→対の失敗、という構成が各節で繰り返されます。常時読む対象としては、適用条件より反復される命令が目立ちます。153行の SKILL.md だけの問題ではなく、毎回読む core を含む量の問題です。

**修正案:** 執筆用の各項目を次の形に縮める。

```text
適用条件:
操作:
成立する例:
詳しい診断: 推敲用ファイルの該当節
```

「なぜ」の長い説明と失敗分類は設計資料へ移し、同じ作業中に変更のない資料を毎回全文再読させない。

## 直さないほうがよい長所

- **品質を点数にしないこと。** `SKILL.md:25`。計測値と作品の良否を分ける境界は維持する。
- **生成と診断の情報を分ける設計。** `SKILL.md:22`。今回必要なのは撤回ではなく、core と実行コンテキストまで含めた実装。
- **横滑り先を一緒に点検すること。** `references/prose-core.md:216`。感情語を減らした結果、身体反応が増える問題を同時に扱っている。
- **作品の契約・既存の声を汎用規則より上に置くこと。** `SKILL.md:21`。契約をパックと例外処理へ確実に通せば、過剰修正を抑えられる。
- **改稿を戻せることと、誤りの訂正を別扱いにすること。** `references/review-protocol.md:185–190`。旧版へ戻しても事実・数え上げの訂正を失わない手順は残す。
